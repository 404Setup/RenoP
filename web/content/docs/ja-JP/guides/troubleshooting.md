# トラブルシューティング

問題が発生した場合は、まず HTTP ステータスコード、正確な URL、リポジトリ形式と公開範囲、認証情報の種類を確認します。
原因を特定する前に複数の設定を一度に変更しないでください。パッケージクライアント側でサーバーからの応答が一般的なエラーメッセージに丸められていることがあります。

## 最小限の証拠を集める

プロセスの再起動や状態の削除を行う前に、次の情報を記録してください。

- RenoP のバージョンと起動時刻。
- リクエスト日時、HTTP メソッド、機密情報を除いた URL、レスポンスのステータスコード。
- リポジトリ名、形式、公開範囲、ミラーや審査の有無。
- クライアント名とバージョン、実行コマンド、秘密情報を除いた詳細ログ。
- 関連するサーバーログと、付与されている場合は `X-Renop-Error-Code` ヘッダー。
- データベースやストレージへの接続可否、空き容量、直近の設定変更内容。

セッション Cookie、API トークン、パスワード、S3/OAuth のアクセスキー、完全な `Authorization` ヘッダーを課題トラッカーやチャット等に貼り付けないでください。

## プロセスが起動しない

まず実行パスと作業ディレクトリを確認します。`renop-settings.db`、SQLite、`index.json`、ローカルストレージの相対パスは、サービス実行環境の作業ディレクトリを基準に解決されるため、対話型シェルでの実行時と異なる場合があります。

よくある原因は、ポートの競合、不正な YAML 構文、到達できないデータベース DSN、書き込み権限の不足、不正な TLS 証明書ファイル、サービス実行アカウントから秘密情報が読み取れないことです。`RENOP_DEFAULT_ADMIN_PASSWORD` は初回の管理者作成時のみ有効であり、既存管理者のパスワード再設定には使用できません。

## ヘルスチェックは成功するが操作できない

```bash
curl -i https://packages.example.com/api/status/health
```

`"UP"` の応答はヘルスチェック用エンドポイントが応答したことのみを示します。ログイン処理、データベース書き込み、ローカル/S3 ストレージ、ミラー連携、公開方針の正常性までは検証されません。認証付きリクエストやテスト用パッケージでの操作を行って確認してください。

管理画面で「新しい操作画面を利用できます」と通知された場合は、Protobuf のデコードやルーティングを疑う前にブラウザを再読み込みしてください。プロキシやブラウザのキャッシュが古いバージョンの JavaScript を保持している可能性があります。

## ステータスコードごとの確認事項

| ステータス | 最初に確認する項目                                                                         |
|:-----------|:-------------------------------------------------------------------------------------------|
| `400`      | 不正な Protobuf/JSON、パスやリソース名の間違い、必須項目の欠落、未対応の操作               |
| `401`      | 認証情報の欠落、期限切れ、形式不正、不許可の認証方式、HTTPS/プロキシ経由で Cookie が返らない |
| `403`      | アカウント権限、トークンのスコープや対象制限、チーム権限レベル、公開範囲、審査権限の不足   |
| `404`      | リポジトリやパスの間違い、非表示リソース、バージョンの不存在、ミラーの取得失敗、非公開データの秘匿 |
| `409`      | 不変バージョン/タグの重複、既存の予約、状態遷移の不整合、並行処理の競合                   |
| `413`      | プロキシまたはサーバーのアップロード上限超過。成果物サイズやバッファリング設定を確認       |
| `429`      | レート制限または同時実行数制御。リトライ案内に従い並列度を下げる                           |
| `5xx`      | データベース、ストレージ、上流ミラー、署名検証、展開処理、内部エラー。サーバーログを確認   |

プレーンテキストのエラーメッセージは人間向けに変更される場合があります。自動化処理ではステータスコードや安定したエラーコードヘッダーを使用してください。

## 認証とブラウザセッション

管理画面の UI は HttpOnly な `renop_session` Cookie を使用します。アカウントセキュリティ等の非公開エンドポイントは、パスワード、Bearer トークン、`Authorization: Session`、URL 内のセッション値を受け付けません。公開オリジンが HTTPS であり、プロキシが元のスキームやホスト情報を正しく転送し、ブラウザが同一オリジンに Cookie を送信していることを確認してください。

自動化（CI/CD）にはスコープ付き Bearer API トークンを使用します。実効権限はトークンスコープ、対象制限、アカウント権限、リポジトリ方針、パッケージチーム権限の共通部分（AND）となります。トークンのスコープだけを広げても、アカウントやチームの権限不足は解決しません。

## Maven と Gradle

- リポジトリ URL の末尾は RenoP のリポジトリ名であり、`/api` ではありません。
- Maven の `<server><id>` は `distributionManagement` または依存リポジトリの ID と一致させる必要があります。
- HTTP Basic 認証のユーザー名にはアカウント名、パスワードには必要なスコープを持つ API トークンを指定します。
- `groupId` が管理対象の公開ドメイン配下にあり、必要なチーム権限レベルが付与されていることを確認します。
- 署名必須のリポジトリでは分離署名とバックエンドの署名記録を確認し、ファイル名だけで判断しないでください。
- 不変リリースの再デプロイ（上書き）は失敗するのが正常な動作です。サーバー上のファイルを直接削除して無理に回避しないでください。

## Cargo

- リポジトリパスと末尾のスラッシュ `/` を含む sparse URL を使用します（例: `sparse+https://packages.example.com/crates/`）。
- `cargo login --registry <name>` を実行し、RenoP のトークン全体を保存します。
- `repository:publish`、`package:create`、ライフサイクル、チーム管理のスコープを適切に使い分けます。
- 上流の名前重複確認が利用できない場合、最初の公開処理は安全のため失敗します。ネットワーク接続の回復後に再試行してください。
- 審査待ちのアーカイブは、承認されるまで sparse インデックスおよび公開カタログには表示されません。

## npm

- レジストリ URL はホスト名だけでなくリポジトリパスまで設定し、必要に応じてスコープごとに設定を分けます。
- ユーザー環境や CI 環境の `.npmrc` 内のトークン設定を確認し、プロジェクトのリポジトリへ誤ってコミットしないでください。
- ポリシーで求められている場合、最初の公開前にパッケージ名を予約してください。
- パッケージバージョンは不変です。並行度を上げてもバージョン競合は解決しません。
- ミラーリングされたパッケージでは、チームや配布タグを変更する前に、上流バージョンとローカル所有権を区別して確認してください。

## Docker と OCI

- レジストリホストにログインし、イメージ名/リポジトリパスは `pull`、`push`、Podman に個別に渡します。
- クライアントが信頼する SSL/TLS 証明書を使用してください。安全でないレジストリ（insecure registry）設定は隔離されたテスト環境のみに留めます。
- ポリシーに応じて、最初の push 前にイメージや名前空間を作成または予約してください。
- プロキシは `/v2/` 認証要求と `/v2/token` トークン交換を保持する必要があります。`Authorization` ヘッダーの削除やパスの書き換えは Bearer 認証フローを破壊します。
- push 失敗時は、ブロブ、マニフェスト、タグのいずれで失敗したかを特定し、ダイジェスト値やメディアタイプをレスポンスと比較してください。

## ミラー、ストレージ、リバースプロキシ

ミラーの取得失敗（miss）は、上流での 404、ネガティブキャッシュ、許可リストによる制限、期限切れの認証情報、送信プロキシの不通、ローカルコミットの失敗などが考えられます。
本番の認証を迂回せず、RenoP サーバーから上流への直接リクエストと、RenoP 経由での取得結果を比較してください。

S3 では、エンドポイント、リージョン、パススタイル、バケット、接頭辞、時刻同期、TLS、読み取り/書き込み/一覧/削除の各権限を確認します。署名付き URL の動作確認はクライアントのネットワーク環境から直接実施してください。ローカルストレージでは所有者権限、空き容量、一時領域の容量、アトミックな名前変更（rename）が可能かを確認します。

大容量のアップロードでは、プロキシのリクエストバッファリングと本文サイズ制限を無効化し、タイムアウト時間を延長してください。転送元ヘッダーは設定済みの信頼できるプロキシからのみ信頼します。

## 問題の切り分けと報告

問題を再現・報告する際は、単一のリポジトリ、テスト用パッケージ、単一のコマンドに絞り込んでください。機密情報を除いた設定内容、期待されるステータスと実際のステータス、プロキシを経由しない直接アクセスの検証結果、実施した復旧手順を含めてください。証拠となるログやデータを保存する前に、データベース、ストレージ、所有権情報を不用意に削除しないでください。

API クライアントの実装については [HTTP API 連携](../api/client-integration.md)、デプロイの検証手順は [本番デプロイチェックリスト](../deployment/production-checklist.md) を参照してください。
